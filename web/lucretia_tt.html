lucretia-tt — time-based 3D PIC tracker

lucretia-tt is a standalone C++/CUDA particle-in-cell tracker designed for the parts of an accelerator that Lucretia's s-based TrackThru cannot model directly: photoinjectors, capture sections, and any region where the bunch is non-relativistic, the longitudinal motion is non-trivial, or 3D space charge dominates. It lives in external/lucretia-tt/ and is invoked from MATLAB via the TimeTrack class.

Built on AMReX + ABLASTR (the BSD-licensed PIC infrastructure shared by WarpX, ImpactX, and HiPACE++); particle dumps use openPMD-api. The end-of-region beam can be handed back to Lucretia's s-based world via freezePlaneOut, ready for the standard TrackThru pipeline.

What it does

  • Cathode emission with thermal MTE and image-charge return force
  • 3D space charge via FFT-based open-BC Poisson (ABLASTR's IGF solver), with a co-moving mesh that follows the bunch in z
  • Field-source elements: analytic (SWCavity, TWCavity, QuadAnalytic, SolenoidAnalytic, UniformB) and 3D-map (FieldMap3D, Solenoid3D, ImpactTField)
  • Boris pusher (relativistic kick-rotate-kick) with adaptive time stepping
  • openPMD HDF5 beam dumps; conversion to Lucretia Beam structs via freezePlaneOut
  • ImpactT lattice import: readImpactTLattice parses an ImpactT.in file (incl. rfdata* field maps) into a lucretia-tt lattice cell array

Target scale: 107 macroparticles routine, 108 occasional, on a single 8×A100 workstation; CPU-MPI also supported.

Setup

macOS — development box

macOS is the supported authoring environment. Single-rank CPU-OMP runs are perfectly usable for tests and small physics experiments; multi-rank CPU-MPI also works. CUDA is Linux-only.

Install the toolchain via Homebrew:

brew install cmake hdf5 ccache libomp
brew install open-mpi      # only if you want to build the cpu-mpi target

Notes:

  • libomp is required because AppleClang doesn't ship native OpenMP. build_tt auto-detects it under /opt/homebrew/opt/libomp (Apple Silicon) or /usr/local/opt/libomp (Intel).
  • Homebrew's hdf5 formula provides serial HDF5. hdf5-mpi conflicts with hdf5 — do not install it. The MPI build of lucretia-tt patches openPMD-api to use serial HDF5 (BeamIO MPI-gathers to rank 0 then writes serially), so the parallel HDF5 package is not needed.
  • openPMD-api itself is FetchContent-built; no Homebrew package needed.
  • ccache is optional but cuts re-build time substantially.

Linux — 8×A100 deployment box

The recommended path is Spack, matching the WarpX-recommended dependency stack. This gives you CUDA-aware MPI (UCX over GPU-direct), parallel HDF5, and openPMD-api in one go. 

git clone --depth=1 https://github.com/spack/spack.git ~/spack
. ~/spack/share/spack/setup-env.sh

spack env create luctt
spack env activate luctt
spack add cmake@3.24:
spack add openmpi+cuda fabrics=ucx
spack add ucx+cuda+gdrcopy+thread_multiple
spack add hdf5@1.14: +mpi +cxx
spack add openpmd-api +mpi +hdf5
spack add cuda@12: cuda_arch=80
spack add ccache
spack install -j 32

Activate the environment in any shell where you build or run:

. ~/spack/share/spack/setup-env.sh
spack env activate luctt

Verify CUDA-aware MPI is enabled:

ompi_info --parsable --all | grep mpi_built_with_cuda_support:value
# expected:
# mca:mpi:base:param:mpi_built_with_cuda_support:value:true

A bare-metal install (apt/yum) also works if you already have a recent CUDA toolkit, OpenMPI built with CUDA support, and HDF5 development headers on the system. The minimum required versions are CMake 3.24, HDF5 1.14, OpenMPI 4.x, and CUDA 12.

Building

Builds are driven from MATLAB via build_tt, which lives at src/TimeTracking/build_tt.m. It runs CMake under the hood, handles platform-specific compiler flags (libomp, mpicxx wrappers), and stages the resulting binary into src/TimeTracking/ for which()-based discovery.

Build targets

Command Backend MPI Build dir Staged binary Platform
build_tt cpu OpenMP off build/ lucretia-tt Mac, Linux
build_tt cpu-mpi OpenMP on build_mpi/ lucretia-tt_mpi Mac, Linux
build_tt gpu CUDA off build/ lucretia-tt Linux
build_tt gpu-mpi CUDA on build_mpi/ lucretia-tt_mpi Linux

Modifiers (any combination):

  • clean — rm -rf build/ before configuring
  • debug — CMAKE_BUILD_TYPE=Debug (default Release)
  • nofft — skip the FFT-based Poisson solver (early bring-up only)
  • noopmd — skip openPMD I/O (early bring-up only)
  • opmd-mpi — build openPMD-api with parallel HDF5 (LucretiaTT_OPENPMD_MPI=ON). Requires hdf5-mpi installed. Default off; see Parallel HDF5 (opt-in) below.
  • verbose — pass --verbose to cmake --build

Examples

From the MATLAB prompt, with Lucretia on the path:

build_tt cpu                   % macOS dev: fastest path to a working binary
build_tt cpu-mpi clean         % full CPU+MPI rebuild from scratch
build_tt gpu-mpi               % Linux: 8x A100 production target
build_tt gpu nofft noopmd      % Linux: smoke test the CUDA pipeline only

Equivalent direct CMake invocation (for CI or shell-only environments):

cd external/lucretia-tt
cmake -S . -B build \
      -DLucretiaTT_COMPUTE=CUDA \
      -DLucretiaTT_MPI=ON \
      -DLucretiaTT_FFT=ON \
      -DCMAKE_CUDA_ARCHITECTURES=80 \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 16

On the first build, AMReX, ABLASTR, and openPMD-api are fetched and built via FetchContent — expect 15–25 minutes. Subsequent rebuilds are incremental and ccache-accelerated; touching one source file usually takes <30 seconds.

Running

Driving lucretia-tt from MATLAB uses the TimeTrack class (src/TimeTracking/@TimeTrack). It writes a ParmParse input file, invokes the staged binary, and reads back the openPMD dumps.

Minimal example: cyclotron in a uniform Bz

tt = TimeTrack();
tt.lattice = { ...
    timetracking.UniformB('name','B','Bz',1e-3), ...
    timetracking.BeamMonitor('name','m','dump_every',100) };
tt.beam = struct('n_particles',1, ...
                 'x',0,'y',0,'z',0, ...
                 'ux',1e7,'uy',0,'uz',0);
tt.geom_lo    = [-0.1, -0.1, -0.1];
tt.geom_hi    = [ 0.1,  0.1,  0.1];
tt.geom_ncell = [16, 16, 16];
tt.dt = 35.7e-12;     % T_c / 1000
tt.n_steps = 1000;
tt.run();
bunches = tt.readDumps();   % cell array of per-step structs

Multi-rank MPI runs

After building cpu-mpi (Mac or Linux) or gpu-mpi (Linux):

tt = TimeTrack();
% ... lattice / beam / geometry as before ...
tt.mpi_nranks = 8;          % auto-picks lucretia-tt_mpi alongside lucretia-tt
tt.run();

Notes on resource sharing:

  • If you set mpi_nranks > 1 with the default OMP_NUM_THREADS (usually = number of cores), each rank will spawn that many OpenMP threads, oversubscribing the box. Set OMP_NUM_THREADS in the shell that launches MATLAB so each rank gets a fair share. On macOS for an 8-core box with mpi_nranks=2, that means OMP_NUM_THREADS=4.
  • mpirun is auto-located: /opt/homebrew/bin/mpirun, then /usr/local/bin/mpirun, then PATH. Override with tt.mpirun_bin = '/path/to/mpirun'.
  • On Linux SLURM clusters, you typically want srun not mpirun. Set tt.mpirun_bin = 'srun'; it'll be invoked as srun -np N ….

GPU runs (Linux only)

The Linux box auto-uses CUDA when you build with build_tt gpu or gpu-mpi. From MATLAB, the workflow is identical to the CPU case — the staged binary handles GPU-vs-CPU transparently. 

% After build_tt gpu-mpi on the Linux box
tt = TimeTrack();
% ... lattice / beam / geometry ...
tt.mpi_nranks = 8;          % one rank per A100
tt.run();

AMReX places one MPI rank on each visible GPU. If you want to limit which GPUs are used, set CUDA_VISIBLE_DEVICES in the launching shell.

Lattice elements

Lattice elements are MATLAB structs created by helper functions in the +timetracking package. A lattice is a cell array of such structs, evaluated in order at each time step.

Output and handoff to Lucretia

Reading dumps

bunches = tt.readDumps();
% bunches{k}.x  - x positions (m)
% bunches{k}.px - px momenta (kg.m/s)
% bunches{k}.q, .w - charge and weight per macroparticle
% bunches{k}.time, .step - simulation time and step index

Freeze-plane handoff to TrackThru

To convert a captured time-based dump into a Lucretia Beam struct that TrackThru can consume: 

beam = tt.freezePlaneOut('last');     % use the last dump
% beam.Bunch.x is the standard 6 x N matrix:
%   row 1: x   (m)
%   row 2: x' = px / pz   (rad)
%   row 3: y   (m)
%   row 4: y' = py / pz
%   row 5: z   (m, centred on the bunch)
%   row 6: P   (GeV/c)
% beam.Bunch.Q is per-macroparticle charge in Coulombs.

% Hand off to standard Lucretia tracking:
[stat, beam_out] = TrackThru(elem1, elem2, beam, 1, 1);

The conversion takes the dump at a fixed time, not a fixed s. For bunches that are short longitudinally compared to their transit length scale (the typical photo-injector handoff case), this is exact. A truly z-triggered freeze plane that drift-corrects each particle to a common s is a future refinement.

Parallel HDF5 (opt-in)

By default, lucretia-tt builds openPMD-api with serial HDF5 even when the application itself is built with MPI. BeamIO MPI-gathers every rank's particles to rank 0 and then writes serially. This is the only mode that works on macOS (Homebrew's serial hdf5 formula conflicts with hdf5-mpi) and is the safest default everywhere.

The cost is rank-0 serial I/O on every dump. For the design scale (107 macros, infrequent dumps) this is a fraction of a second per dump — invisible. At 109+ macros with frequent dumps, the rank-0 serial path becomes a real bottleneck.

On Linux with parallel HDF5 already installed (Spack hdf5+mpi, or apt libhdf5-mpi-dev), build with opmd-mpi to skip the patch and let openPMD-api use parallel HDF5: 

build_tt gpu-mpi opmd-mpi clean

With LucretiaTT_OPENPMD_MPI=ON, openPMD-api links against parallel HDF5 and a future BeamIO rewrite can use collective parallel writes (each rank stores its local chunk to a global offset, with a single collective flush). Until that refactor lands, BeamIO still uses the rank-0 gather path even with opmd-mpi — so the build switch alone doesn't change I/O perf, it just unblocks the follow-up. Watch the issue tracker or ping the maintainers if you hit I/O as a bottleneck.

Testing

The tests/ directory holds a regression suite. Each test is a MATLAB function returning a single boolean ok. 

cd Lucretia/src/TimeTracking/tests

% Run them all (skipping the slow trackthru_handoff cross-check):
results = run_all_tests('exclude', {'test_trackthru_handoff'});

% Or run one:
ok = test_cyclotron();
ok = test_uniform_sphere();      % SC validation
ok = test_freezeplane_handoff(); % Phase 5 round-trip

For MPI builds, test_mpi_smoke runs cyclotron, uniform-sphere, and freezeplane both at np=1 and np=2 and confirms the two give bit-for-bit identical results.

Troubleshooting

macOS — libomp not found

AppleClang has no built-in OpenMP. Run brew install libomp. build_tt looks under /opt/homebrew/opt/libomp (Apple Silicon) or /usr/local/opt/libomp (Intel).

macOS MPI build — MPI compiler wrappers not found

Run brew install open-mpi. The wrappers mpicc and mpicxx need to be in /opt/homebrew/bin or /usr/local/bin.

MPI launch warning — oversubscribing CPU cores with OMP threads

AMReX warns when (num_ranks × OMP_NUM_THREADS) > num_cores. Set OMP_NUM_THREADS in the shell that launches MATLAB so each rank gets a fair share, e.g. OMP_NUM_THREADS=4 matlab… for an 8-core box with mpi_nranks=2.

MPI run — no MPI binary found

You set tt.mpi_nranks > 1 but lucretia-tt_mpi isn't in src/TimeTracking/. Build it: build_tt cpu-mpi on Mac, build_tt gpu-mpi on Linux.

Linux GPU build — wrong CUDA arch

build_tt gpu defaults to whatever AMReX's CMake picks automatically. For the 8×A100 box explicitly pass -DCMAKE_CUDA_ARCHITECTURES=80 via the direct CMake invocation, or update build_tt.m to inject it for the gpu targets.

Run completes but readDumps returns empty

The most common cause is a particle bunch that drifts past the BeamMonitor without ever overlapping its time window, or an emission pulse that fires entirely outside the simulation window. Check tt.last_log for the per-step particle count printed by the BeamMonitor.
