Overview #

lucretia-tt is a standalone C++/CUDA particle-in-cell tracker designed for the parts of an accelerator that Lucretia's s-based TrackThru cannot model directly: photoinjectors, capture sections, and any region where the bunch is non-relativistic, the longitudinal motion is non-trivial, or 3D space charge dominates. It lives in external/lucretia-tt/ and is invoked from MATLAB via the TimeTrack class.

Built on AMReX + ABLASTR (the BSD-licensed PIC infrastructure shared by WarpX, ImpactX, and HiPACE++); particle dumps use openPMD-api. The end-of-region beam can be handed back to Lucretia's s-based world via freezePlaneOut, ready for the standard TrackThru pipeline.

What it does #

  • Cathode emission with thermal MTE and image-charge return force
  • 3D space charge via FFT-based open-BC Poisson (ABLASTR's IGF solver) with a precomputed self-force lookup table; co-moving SC mesh that follows the bunch in z
  • Field-source elements: analytic (SWCavity, TWCavity, QuadAnalytic, SolenoidAnalytic, UniformB) and 3D-map (FieldMap3D, Solenoid3D, ImpactTField)
  • Boris pusher (relativistic kick-rotate-kick) with optional variable-dt schedule (small dt in the cathode/gun region, large dt past the relativistic transition)
  • openPMD HDF5 beam dumps; conversion to Lucretia Beam structs via freezePlaneOut
  • ImpactT compatibility: readImpactTLattice parses an ImpactT.in file (incl. rfdata* field maps and variable-dt schedule) into a lucretia-tt setup; CathodeLaserDist generates ImpactT-format partcl.data from a Hammersley low-discrepancy sampler (no clumping)

Target scale: 107 macroparticles routine, 108 occasional, on a multi-GPU workstation; CPU-MPI also supported and practical at production scale (a 96-physical-core machine completes a 5×107-macro / 1000-step run with space charge in roughly 15 minutes).

Setup #

macOS — development box

macOS is the supported authoring environment. Single-rank CPU-OpenMP runs are perfectly usable for tests and small physics experiments; multi-rank CPU-MPI also works for benchmarking the MPI path before you deploy. CUDA is Linux-only.

Install the toolchain via Homebrew:

brew install cmake hdf5 ccache libomp
brew install open-mpi      # only if you want to build the cpu-mpi target

Notes:

  • libomp is required because AppleClang doesn't ship native OpenMP. build_tt auto-detects it under /opt/homebrew/opt/libomp (Apple Silicon) or /usr/local/opt/libomp (Intel).
  • Homebrew's hdf5 formula provides serial HDF5. hdf5-mpi conflicts with hdf5 — do not install it. The MPI build of lucretia-tt patches openPMD-api to use serial HDF5 (BeamIO MPI-gathers to rank 0 then writes serially), so the parallel HDF5 package is not needed.
  • openPMD-api itself is FetchContent-built; no Homebrew package needed.
  • ccache is optional but cuts re-build time substantially.

Linux — CPU production / dev

For pure-CPU production runs (any modern x86-64 Linux distribution; tested on Ubuntu 22.04+) the dependency stack is the standard distro packages, plus a recent CMake. 

# CMake -- Kitware repo if your distro ships < 3.24
sudo apt install -y ca-certificates gpg wget
wget -O - https://apt.kitware.com/keys/kitware-archive-latest.asc 2>/dev/null \
  | sudo gpg --dearmor -o /usr/share/keyrings/kitware-archive-keyring.gpg
echo 'deb [signed-by=/usr/share/keyrings/kitware-archive-keyring.gpg] https://apt.kitware.com/ubuntu/ jammy main' \
  | sudo tee /etc/apt/sources.list.d/kitware.list
sudo apt update && sudo apt install -y cmake

# Toolchain + dependencies
sudo apt install -y build-essential git ccache pkg-config \
                    libhdf5-dev libopenmpi-dev openmpi-bin libomp-dev

Verify versions: cmake --version ≥ 3.24, mpirun --version shows OpenMPI 4.x or 5.x. Serial HDF5 (libhdf5-dev) is enough for the default build — the openPMD-MPI patch keeps I/O on rank 0.

Linux — GPU build

For GPU runs, you additionally need a CUDA toolkit (12.x), a CUDA-aware MPI implementation (for multi-GPU runs with GPU-direct), and compatible NVIDIA drivers.

The two well-trodden paths:

NVIDIA HPC SDK (apt repo)
Bundles CUDA toolkit + CUDA-aware OpenMPI + math libs in one shot. Sidesteps the fact that distro openmpi-bin is not CUDA-aware out of the box. After install, add the SDK's mpi/bin and cuda/bin to your PATH and the cuda/lib64 to LD_LIBRARY_PATH.
Spack
Slower first-install (~1–2 h on a fast box) but more flexible. Build a Spack environment with cuda, openmpi+cuda fabrics=ucx, ucx+cuda+gdrcopy, hdf5+mpi, openpmd-api+mpi+hdf5, and your target cuda_arch=<sm_NN>.

Verify CUDA-aware MPI is enabled before relying on multi-GPU runs:

nvidia-smi                                # GPUs visible, drivers OK
nvcc --version                            # CUDA 12.x
ompi_info --parsable --all | grep mpi_built_with_cuda_support:value
# expected:
# mca:mpi:base:param:mpi_built_with_cuda_support:value:true

Pass the appropriate CUDA architecture flag to CMake when building — e.g. -DCMAKE_CUDA_ARCHITECTURES=80 for Ampere, =90 for Hopper. build_tt gpu defers to AMReX's auto-detection, which usually does the right thing if you have the GPU visible at build time; pass the flag explicitly via direct CMake (see Building) if you need to target a specific arch.

Building #

Builds are driven from MATLAB via build_tt, which lives at src/TimeTracking/build_tt.m. It runs CMake under the hood, handles platform-specific compiler flags (libomp, mpicxx wrappers), and stages the resulting binary into src/TimeTracking/ for which()-based discovery.

Build targets

CommandBackendMPIBuild dirStaged binaryPlatform
build_tt cpu OpenMPoffbuild/ lucretia-tt Mac, Linux
build_tt cpu-mpi OpenMPon build_mpi/ lucretia-tt_mpi Mac, Linux
build_tt gpu CUDA offbuild_gpu/ lucretia-tt_gpu Linux
build_tt gpu-mpi CUDA on build_gpu_mpi/ lucretia-tt_gpu_mpiLinux

Modifiers (any combination):

  • clean — rm -rf the target's build dir before configuring. With no target given (build_tt clean), removes every existing build dir under external/lucretia-tt/ and exits without rebuilding.
  • debug — CMAKE_BUILD_TYPE=Debug (default Release)
  • nofft — skip the FFT-based Poisson solver (early bring-up only)
  • noopmd — skip openPMD I/O (early bring-up only)
  • opmd-mpi — build openPMD-api with parallel HDF5 (LucretiaTT_OPENPMD_MPI=ON). See Parallel HDF5 (opt-in).
  • verbose — pass --verbose to cmake --build

Examples

build_tt cpu                   % macOS dev: fastest path to a working binary
build_tt cpu-mpi clean         % full CPU+MPI rebuild from scratch
build_tt gpu-mpi               % Linux: GPU production target
build_tt clean                 % nuke every build dir; no rebuild

Equivalent direct CMake invocation (for CI or shell-only environments):

cd external/lucretia-tt
cmake -S . -B build_gpu_mpi \
      -DLucretiaTT_COMPUTE=CUDA \
      -DLucretiaTT_MPI=ON \
      -DLucretiaTT_FFT=ON \
      -DCMAKE_CUDA_ARCHITECTURES=<your_sm_arch> \
      -DCMAKE_BUILD_TYPE=Release
cmake --build build_gpu_mpi -j

On the first build, AMReX, ABLASTR, and openPMD-api are fetched and built via FetchContent — expect 15–25 minutes. Subsequent rebuilds are incremental and ccache-accelerated; touching one source file usually takes < 30 seconds.

Running #

Driving lucretia-tt from MATLAB uses the TimeTrack class (src/TimeTracking/@TimeTrack). It writes a ParmParse input file, invokes the staged binary, and reads back the openPMD dumps.

Minimal example: cyclotron in a uniform Bz

tt = TimeTrack();
tt.lattice = { ...
    timetracking.UniformB('name','B','Bz',1e-3), ...
    timetracking.BeamMonitor('name','m','dump_every',100) };
tt.beam = struct('n_particles',1, ...
                 'x',0,'y',0,'z',0, ...
                 'ux',1e7,'uy',0,'uz',0);
tt.geom_lo    = [-0.1, -0.1, -0.1];
tt.geom_hi    = [ 0.1,  0.1,  0.1];
tt.geom_ncell = [16, 16, 16];
tt.dt = 35.7e-12;     % T_c / 1000
tt.n_steps = 1000;
tt.run();
bunches = tt.readDumps();   % cell array of per-step structs

MPI & NUMA setup #

On any multi-socket / multi-NUMA machine, getting MPI ranks pinned to NUMA domains and OpenMP threads bound to physical cores is essential for getting close to the machine's peak throughput. The bench harness (tests/bench_scaling.m) does this automatically; for production runs you set it up yourself.

Inspect the host first

lscpu | grep -E "^(Socket|Core|NUMA node\(s\)|Model name|Thread)"

What to look for:

  • Sockets × Cores per socket — total physical cores
  • Thread(s) per core — usually 2 (hyperthreading); we want OpenMP to use only physical cores
  • NUMA node(s) — can exceed the socket count if Sub-NUMA Clustering (SNC) is enabled. On Intel Xeon Platinum SKUs each socket is often split into 2 NUMA domains, so a 2-socket box reports 4 NUMA nodes

Pick a (ranks, threads) combination

The general rule: one MPI rank per NUMA node, with OMP_NUM_THREADS = (physical cores per NUMA). So on a box with N NUMA nodes of K cores each: 

tt.mpi_nranks         = N;
tt.mpirun_extra_args  = '--bind-to numa --map-by numa';
% In the shell that launches MATLAB:
%   export OMP_NUM_THREADS=K
%   export OMP_PLACES=cores
%   export OMP_PROC_BIND=close

Concrete examples for common Linux machine layouts:

BoxSockets × coresNUMA nodesRecommended (mpi_nranks, OMP_NUM_THREADS)
24-core single socket1 × 241(1, 24)
2-socket, 48-core (no SNC)2 × 482(2, 48)
2-socket, 96-core, SNC=22 × 484(4, 24)
2-socket, 144-core, SNC=22 × 724(4, 36)
8-GPU node (one rank per GPU)——(8, 1) for compute, OMP small

Why these env vars matter

OMP_PLACES=cores
Restricts OpenMP to physical cores rather than hyperthreads. PIC codes have very high cache / memory bandwidth pressure and hyperthread contention usually hurts.
OMP_PROC_BIND=close
Keeps each thread team contiguous within its NUMA, avoiding cross-domain memory traffic.
--bind-to numa --map-by numa
Pins each MPI rank to one NUMA node, so all OpenMP threads in that rank are NUMA-local to the rank's allocated memory. On non-SNC 2-socket boxes --bind-to socket is equivalent; on SNC boxes --bind-to numa is the right choice (and is a no-op on single-NUMA systems).
OMP_NUM_THREADS
Set by you in the shell before launching MATLAB. TimeTrack doesn't override it — what you set is what each rank's thread team gets.

Strong-scaling sweep with bench_scaling

To answer "am I making full use of this machine?" on a fresh box, run a strong-scaling sweep:

cd src/TimeTracking/tests
results = bench_scaling('numa_bind', true);
% Or with a bigger problem to expose the push-bound regime:
results = bench_scaling('macros', 5e7, 'n_steps', 200, 'numa_bind', true);

The harness sweeps several (nranks, threads) combinations on the same problem, sets OMP_PLACES / OMP_PROC_BIND / OMP_NUM_THREADS internally, optionally adds --bind-to numa, and prints a strong- scaling efficiency table. On a multi-NUMA box you should see the one-rank-per-NUMA configuration (e.g. (4, 24) on a 96-core 4-NUMA machine) at the top.

Parallel HDF5 (opt-in) #

By default, lucretia-tt builds openPMD-api with serial HDF5 even when the application itself is built with MPI. BeamIO MPI-gathers every rank's particles to rank 0 and then writes serially. This is the only mode that works on macOS (Homebrew's serial hdf5 conflicts with hdf5-mpi) and is the safest default everywhere.

The cost is rank-0 serial I/O on every dump. For the design scale (107 macros, infrequent dumps) this is a fraction of a second per dump. At 109+ macros with frequent dumps, the rank-0 serial path becomes a real bottleneck.

On Linux with parallel HDF5 already installed (Spack hdf5+mpi, or apt libhdf5-mpi-dev), build with opmd-mpi to skip the patch and let openPMD-api use parallel HDF5: 

build_tt gpu-mpi opmd-mpi clean

With LucretiaTT_OPENPMD_MPI=ON, openPMD-api links against parallel HDF5 and a future BeamIO rewrite can use collective parallel writes (each rank stores its local chunk to a global offset, with a single collective flush). Until that refactor lands, BeamIO still uses the rank-0 gather path even with opmd-mpi, so the build switch alone doesn't change I/O perf — it just unblocks the follow-up.

Lattice elements #

Lattice elements are MATLAB structs created by helper functions in the +timetracking package. A lattice is a cell array of such structs, evaluated in z-order at each time step. Each element specifies its lab-frame z position; the integrator gates the field contribution to the active region.

CathodeSource #

Photoinjector emission source — emits macroparticles from a planar cathode at a given z, with optional self-image-charge plane.

ParamDefaultUnitsMeaning
name'CAT'—Element label
z_cathode0.0mLab-frame z of the cathode plane
image_chargetrueboolEnable image-charge Ez contribution from the conducting plane
n_macroparticles_total0—Total macroparticles to emit (0 disables)
total_charge0.0CTotal bunch charge (sign included)
pulse_shape'gaussian'—'gaussian' (FWHM = pulse_duration) or 'flat_top'
pulse_duration0.0sTemporal pulse width
pulse_t00.0sCentre time of the emission pulse
transverse_profile'gaussian'—'gaussian' (RMS = spot_size) or 'uniform_disk'
spot_size0.0mTransverse spot-size parameter
mte0.0eVMean transverse energy of emitted electrons

Emission is gated by the temporal pulse profile; the optional image-charge plane adds the standard Ez contribution from the conducting cathode surface. The MTE sets the initial thermal transverse momentum spread. Set n_macroparticles_total = 0 to use the element purely as an image-charge plane (with no emission). 

cat = timetracking.CathodeSource('z_cathode', 0, ...
    'n_macroparticles_total', 1000, 'total_charge', 1e-9, ...
    'pulse_shape', 'gaussian', 'pulse_duration', 10e-12, ...
    'pulse_t0', 30e-12, 'transverse_profile', 'gaussian', ...
    'spot_size', 0.5e-3, 'mte', 0.5);

BeamMonitor #

Diagnostic element that writes the full bunch state to an openPMD dump every N integrator steps.

ParamDefaultUnitsMeaning
name'mon'—Element label (used in the openPMD output filename)
dump_every1stepsWrite a dump every N integrator steps (must be ≥ 1)

A monitor records only — it has no field, no length, and does not modify the beam. Cadence is in integrator steps, not time or distance. Multiple monitors with different dump_every can coexist. 

mon = timetracking.BeamMonitor('name', 'm1', 'dump_every', 10);

Drift3D #

Field-free drift segment of fixed length.

ParamDefaultUnitsMeaning
name'drift'—Element label
length1.0mDrift length along z

No field, no aperture — particles propagate purely under their existing momentum. Used to set the spacing between active elements in the z-ordered lattice. 

d1 = timetracking.Drift3D('name', 'd1', 'length', 1.0);

QuadAnalytic #

Hard-edge magnetic quadrupole with a linear analytic field profile.

ParamDefaultUnitsMeaning
name'Q'—Element label
z0.0mLab-frame z of the upstream face
length0.1mActive length along z
gradient0.0T/mQuadrupole gradient G

Inside the active region the field is B_x = G·y, B_y = G·x. Hard edges: the field is exactly zero outside [z, z+length]; no fringe-field model. Sign of gradient sets focusing / defocusing plane. 

q1 = timetracking.QuadAnalytic('z', 0.5, 'length', 0.1, 'gradient', 5.0);

SolenoidAnalytic #

Solenoid with a Gaussian on-axis Bz profile, with paraxial off-axis extension.

ParamDefaultUnitsMeaning
name'SOL'—Element label
z0.0mLab-frame z of the upstream face
length0.2mActive length along z
peak_Bz0.0TPeak on-axis longitudinal field
sigma0.03mGaussian sigma of the longitudinal profile
z_peaklength/2mPeak position relative to element start (default = midpoint)

On-axis field is B_z = peak_Bz · exp(-((z_local - z_peak)/sigma)2). Off-axis the radial component uses the paraxial approximation B_r = -(r/2) dB_z/dz, which holds for r << sigma. z_peak is measured from the element's upstream face. 

sol = timetracking.SolenoidAnalytic('z', 0.5, 'length', 0.2, ...
    'peak_Bz', 0.1, 'sigma', 0.03, 'z_peak', 0.1);

Solenoid3D #

Solenoid driven by a measured/simulated 2D Bz(r,z) map loaded from HDF5.

ParamDefaultUnitsMeaning
name'SOL3D'—Element label
z0.0mLab-frame z of the upstream face
length0.2mActive length along z
pathrequired—Path to HDF5 field map

The HDF5 file (lucretia-tt schema) supplies /Bz shape (Nz, Nr), /grid_spacing = [dr, dz], and /grid_origin = [r0, z0] (relative to element start; r0 is typically 0). B_r is reconstructed paraxially from dB_z/dz at gather time, so accuracy degrades for large r/sigma. Use timetracking.writeFieldMap2D to author test files. 

sol3d = timetracking.Solenoid3D('z', 0.5, 'length', 0.2, ...
    'path', 'sol_map.h5');

UniformB #

Uniform constant magnetic field — primarily a unit-test / debug element.

ParamDefaultUnitsMeaning
name'UB'—Element label
Bx0.0Tx-component of field
By0.0Ty-component of field
Bz0.0Tz-component of field

Returns a constant field everywhere this element is queried by the integrator. No spatial or temporal variation. Useful for cyclotron regression tests and quick sanity checks. 

ub = timetracking.UniformB('name', 'sol1', 'Bz', 0.01);

SWCavity #

Analytic N-cell π-mode standing-wave RF cavity (paraxial 3D extension of the on-axis Ez).

ParamDefaultUnitsMeaning
name'SW'—Element label
z0.0mLab-frame z of the upstream face
length0.1mActive length
n_cells1—Number of π-mode cells (≥ 1)
f_RF2.856e9HzRF frequency
peak_field0.0V/mPeak on-axis Ez
phase0.0radRF phase offset

On-axis E_z = peak_field · sin(Nπ zlocal/length) · cos(ω t + phase); transverse E and B are reconstructed paraxially from Maxwell's equations. Note: the pure-sine longitudinal envelope cannot extract cold electrons from a cathode (no Ez at zlocal = 0). For gun-quality field profiles use ImpactTField or FieldMap3D. 

sw = timetracking.SWCavity('z', 0, 'length', 0.1, 'n_cells', 1, ...
    'f_RF', 2.856e9, 'peak_field', 100e6, 'phase', 0);

TWCavity #

Forward-propagating TM travelling-wave RF cavity at constant amplitude.

ParamDefaultUnitsMeaning
name'TW'—Element label
z0.0mLab-frame z of the upstream face
length0.1mActive length
f_RF2.856e9HzRF frequency
peak_field0.0V/mOn-axis Ez amplitude
phase0.0radRF phase offset
v_phasecm/sPhase velocity along z

On-axis E_z = peak_field · cos(ω t - k_z zlocal + phase) with k_z = ω/v_phase. Constant amplitude (no envelope/taper). For v_phase = c the wave is matched to a relativistic beam; deviation from c is the only handle for synchronous-phase tuning here. 

tw = timetracking.TWCavity('z', 0, 'length', 0.1, ...
    'f_RF', 2.856e9, 'peak_field', 100e6, 'phase', 0);

ImpactTField #

Element backed by an ImpactT-format rfdata Fourier field map (Ez and/or Bz) — used for both RF cavities and DC solenoids.

ParamDefaultUnitsMeaning
name'IT'—Element label
z0.0mLab-frame z that maps to the file's intrinsic z = 0
pathrequired—Path to the ImpactT rfdata file
scale_E0.0V/mScale on the on-axis Ez Fourier sum
scale_B0.0TScale on the on-axis Bz Fourier sum
f_RF0.0HzRF frequency (0 → static field)
phase_deg0.0degRF phase offset (converted to radians for the kernel)

The rfdata file contains two Fourier blocks (Ez then Bz). The element is gated to zlab ∈ [z + zmin, z + zmax], where zmin/zmax come from the file. Time dependence is cos(2π f_RF t + phase_rad) on both fields; with f_RF = 0 it collapses to a constant cos(phase_rad) — that's how solenoids work. Note that z maps the file's intrinsic z = 0, so to place a gun cathode you set z_cathode = z + zmin, not z. 

% RF gun (2.856 GHz)
gun = timetracking.ImpactTField('z', 0, 'path', 'rfdata201', ...
    'scale_E', 4.75282e7, 'f_RF', 2.856e9, 'phase_deg', 304.668);

% DC bucking solenoid
buck = timetracking.ImpactTField('z', 0.0422, 'path', 'rfdata102', ...
    'scale_B', 0.219982);

FieldMap3D #

Generic 3D Cartesian field-map element loaded from a lucretia-tt-schema HDF5 file, optionally RF-modulated.

ParamDefaultUnitsMeaning
name'FM3D'—Element label
z0.0mLab-frame z of the upstream face
length0.1mActive length
pathrequired—Path to HDF5 field map
rf_modulatedfalseboolMultiply field by cos(ω t + phase)
f_RF0.0HzRF frequency (used if rf_modulated)
phase0.0radRF phase offset

The HDF5 file provides at least one of /Bx /By /Bz or /Ex /Ey /Ez as datasets shaped (Nz, Ny, Nx) (matches MATLAB's natural axis order — C++ readers consume the same), plus /grid_spacing = [dx, dy, dz] and /grid_origin = [x0, y0, z0] relative to the element start z. With rf_modulated = true the entire static map is multiplied by a single time-harmonic factor. Use timetracking.writeFieldMap3D to author test files. 

% Static map
fm = timetracking.FieldMap3D('z', 0, 'length', 0.1, 'path', 'fields.h5');

% RF-modulated cavity map
rfm = timetracking.FieldMap3D('z', 0, 'length', 0.1, ...
    'path', 'rf_cavity.h5', 'rf_modulated', true, ...
    'f_RF', 2.856e9, 'phase', 0);

SeedBeam #

Initial bunch specification — not a lattice element, but the input particle source for TimeTrack. Two modes: simple colocated bunch, or a custom HDF5 seed.

ParamDefaultUnitsMeaning
n_particles1—Macroparticle count for the colocated mode
x / y / z0.0mInitial position
ux / uy / uz0.0m/sProper-velocity components (u = γ v)
weight1.0—Per-macroparticle weight
seed_file''—Path to HDF5 bunch file (custom mode)

Components are proper velocities (u = γ v), not lab velocities. The beamline direction is +z, so a forward beam has nonzero uz. Charge and mass default to electron values inside the kernel. Pass seed_file to override the colocated mode with a fully custom bunch authored by timetracking.writeBunchSeed or CathodeLaserDist.writeBunchSeedH5. 

% Simple colocated bunch
b = timetracking.SeedBeam('n_particles', 1, 'uz', 1e7);

% Custom bunch from HDF5
b = timetracking.SeedBeam('seed_file', '/tmp/bunch.h5');

Cathode beam generation #

For photoinjector simulations, CathodeLaserDist (src/BeamGeneration/) generates the initial particle distribution at the cathode. Pure MATLAB — no Python dependency. Uses a Hammersley low-discrepancy sequence in 5D so neighbouring macroparticles are quasi-uniformly spaced (no clumping that would otherwise drive micro-bunch instabilities in PIC simulation).

Distributions supported, independently for transverse and longitudinal:

  • Gaussian — standard Normal, sigma controls scale
  • Super-Gaussian — alpha=0.5 Gaussian-like with mild flat-top, alpha→0 uniform-with-edges (matches distgen's deformable convention)
  • Uniform — flat in [-W, W] (transverse: disc r in [0, R])

Cathode emission adds Maxwell-Boltzmann transverse momenta with mean transverse energy MTE [eV]; pz is half-Maxwell with a min cutoff to avoid trapped particles.

c = CathodeLaserDist();
c.n_particles = 1e5;
c.sigma_xy    = 475e-6;        c.r_type = 'super_gaussian';  c.r_alpha = 0.5;
c.sigma_t     = 7e-12;         c.t_type = 'super_gaussian';  c.t_alpha = 0.5;
c.t_slope     = -0.142581;     c.r_truncate = 1.3;
c.Q_total     = 1e-9;          c.MTE = 0.414;
Beam = c.generate();

c.writePartclData('partcl.data');     % ImpactT-format text
c.writeBunchSeedH5('seed.h5');        % lucretia-tt HDF5 seed

Output and handoff to Lucretia #

Reading dumps

bunches = tt.readDumps();
% bunches{k}.x  - x positions (m)
% bunches{k}.px - px momenta (kg.m/s)
% bunches{k}.q, .w - charge and weight per macroparticle
% bunches{k}.time, .step - simulation time and step index

Freeze-plane handoff to TrackThru

To convert a captured time-based dump into a Lucretia Beam struct that TrackThru can consume: 

beam = tt.freezePlaneOut('last');     % use the last dump
% beam.Bunch.x is the standard 6 x N matrix:
%   row 1: x   (m)
%   row 2: x' = px / pz   (rad)
%   row 3: y   (m)
%   row 4: y' = py / pz
%   row 5: z   (m, centred on the bunch)
%   row 6: P   (GeV/c)
% beam.Bunch.Q is per-macroparticle charge in Coulombs.

% Hand off to standard Lucretia tracking:
[stat, beam_out] = TrackThru(elem1, elem2, beam, 1, 1);

The conversion takes the dump at a fixed time, not a fixed s. For bunches that are short longitudinally compared to their transit length scale (the typical photo-injector handoff case), this is exact. A truly z-triggered freeze plane that drift-corrects each particle to a common s is a future refinement.

Testing #

The tests/ directory holds a regression suite. Each test is a MATLAB function returning a single boolean ok. 

cd Lucretia/src/TimeTracking/tests

% Run them all (skipping the slow trackthru_handoff cross-check):
results = run_all_tests('exclude', {'test_trackthru_handoff'});

% Or run one:
ok = test_cyclotron();
ok = test_uniform_sphere();      % SC validation
ok = test_freezeplane_handoff(); % cathode -> drift -> freezePlaneOut

For MPI builds, test_mpi_smoke runs cyclotron, uniform-sphere, and freezeplane both at np=1 and np=2 and confirms the two give bit-for-bit identical results.

Troubleshooting #

macOS — libomp not found

AppleClang has no built-in OpenMP. Run brew install libomp. build_tt looks under /opt/homebrew/opt/libomp (Apple Silicon) or /usr/local/opt/libomp (Intel).

macOS MPI build — MPI compiler wrappers not found

Run brew install open-mpi. The wrappers mpicc and mpicxx need to be in /opt/homebrew/bin or /usr/local/bin.

Linux — cmake: GLIBCXX_3.4.32 not found

MATLAB on Linux ships its own (older) libstdc++ / libcurl in $matlabroot/sys/os/glnxa64 and prepends them to LD_LIBRARY_PATH for child processes. Newer system tools (cmake, gcc) need the host's libstdc++. build_tt handles this automatically by stripping MATLAB-rooted entries from LD_LIBRARY_PATH when spawning cmake / make / the lucretia-tt binary itself. If you hit the error, pull a recent build_tt.m — the fix lives in the helper +timetracking/linux_matlab_env_prefix.m.

MPI launch warning — oversubscribing CPU cores with OMP threads

AMReX warns when (num_ranks × OMP_NUM_THREADS) > num_cores. Set OMP_NUM_THREADS in the shell that launches MATLAB so each rank gets a fair share. See MPI & NUMA setup.

MPI run — no MPI binary found

You set tt.mpi_nranks > 1 but the corresponding MPI binary isn't in src/TimeTracking/. Build it: build_tt cpu-mpi or build_tt gpu-mpi. The error message includes the exact build_tt command for the requested target+MPI combination.

MPI run — Permission denied / cannot execute binary

The staged binary is missing +x, or it's a binary built for a different architecture (e.g. an arm64 macOS build copied onto a Linux x86 box via rsync). Check with file and ls -la; rebuild fresh on the actual target host with build_tt cpu clean.

Run completes but readDumps returns empty

The most common cause is a particle bunch that drifts past the BeamMonitor without ever overlapping its time window, or an emission pulse that fires entirely outside the simulation window. Check tt.last_log for the per-step particle count printed by the BeamMonitor. Also make sure tt.t_start aligns with the bunch's expected emission time when seeding from CathodeLaserDist or an ImpactT-derived configuration.
