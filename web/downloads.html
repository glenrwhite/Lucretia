Downloads / Source code description

The Lucretia code is open-source:  anyone can freely download any or all of the source, examples, binaries, etc.  Links to facilitate downloading are below.  The philosophy of the Lucretia maintainers is to keep binaries (mex files) for the CURRENT version of Matlab only in the download package and file repository. All development and bugfixes/maintainance etc are done using the current Matlab release. Although most m-files, and to a lesser extent the mexfiles, will probably work for several versions back from the current one, we cannot guarantee this as supported functions and the Matlab build environment change over time.
Two sets of mexfiles are maintained, if you wish to use the GEANT4 interface an additional setup step is required after downloading (see below).

Supported Environments

Any environment supported by Matlab should be OK for running Lucretia: Mathworks product support information for all Matlab versions can be found here. We supply build files and the source code for compiling all included mexfiles, if the supplied mexfiles do not work for you in your environment, see the section below to building mex files from source. The supplied mex file binaries are built under the current latest Matlab version,
NB: Currently the GEANT4 compatible binaries are only supplied for the Linux environment.

Note on use with GEANT4 subroutines: (only available currently under linux)
To run the GEANT4 compatible versions of the Lucretia mex files, run the LucretiaInit.m function with the 'cpu-g4' argument in your Matlab session.
If you wish to make use of the GEANT4 calling subroutines, you must also have the required GEANT4 data files. For the tar distributions, these are packaged along with the Lucretia distrubution and you will get these automatically when you extract the everything else. If you are using code checked out from the subversion repository, you need to separately download and unpack the G4Data files into the ExtProcess directory:
  • Download G4Data tarball from here into Lucretia/src/ExtProcess directory
  • $ cd Lucretia/src/ExtProcess
  • $ tar --bzip2 -xf G4Data.tar-bz2
mexfile Source

The source code for Lucretia binary mex files exists as several c, c++, and fortran files all contained in the Lucretia/src/mexsrc directory and subdirectories therein. The "core" Lucretia binaries are built in the mexsrc directory itself from c source files. See here for a description of these mexfiles. There is a build.m file in the mexsrc file which is designed to be run from within a Matlab session and builds Lucretia using the mex compiler defined in the Matlab session for any supported operating system. Follow Matlab instructions for setting up your mex environment, then see build instructions in the build.m function file. There is also a system Makefile included in the mexsrc directory for building.
There are separate directories containing the source code for the XSIF parser (mexsrc/xsif) and for the Ground Motion code (mexsrc/matgm). These source files are fortran77 and fortran90 based. Once again there are self-describing Makefiles in each of these build directories. There is also a seperate directory for the source for the GEANT4 interface module, contained in the src/mexsrc/g4track directory. To build against this to enable the GEANT4 process function to work from within Lucretia: first build the g4track library object using the Makefile in that directory (assumes GEANT4 v.10+ is installed on your system). Then build Lucretia using the "make g4track" command. The distributed TrackThru mex files (for linux 64-bit) are built including the GEANT4 libraries.
The only known fortran compiler which works with current versions of Matlab and these source files is the Intel fortran compiler.
Run-time libraries for the Intel compiler and other required shared object libraries are kept in the Lucretia/src/Libs directory (each environment has a sub-directory). You should add the relevant Libs directory to your shared object search path (LD_LIBRARY_PATH environment variable for Linux-based operating systems, PATH for windows or DYLD_LIBRARY_PATH for Mac) before starting Matlab to successfully run all mexfiles.

Build options (build.m)

The build script src/mexsrc/build.m accepts the following arguments, which can be combined as space-separated tokens (for example build cpu omp fast install).  Any argument not listed below is ignored.

Argument Category Effect / requirement
cpu Target Default CPU build (no GEANT4, no GPU). Compiles all mex entry points: GetRmats, GetTwiss, RmatAtoB, TrackThru, VerifyLattice, SeedLucretiaRng.  Requires only a working Matlab mex compiler.
cpu-g4 Target CPU build with GEANT4 secondary-particle tracking enabled in TrackThru.  Requires GEANT4 v10+ installed with the geant4-config script on the system PATH, and the static library src/mexsrc/g4track/libg4track.a built previously (see the GEANT4 section above).  Linux only at present.
gpu Target CUDA build of TrackThru via mexcuda.  Requires:
  • NVIDIA GPU with CUDA compute capability 2.0+ and current CUDA drivers,
  • Matlab Parallel Computing Toolbox,
  • matching CUDA Toolkit (Mathworks publishes the supported version per Matlab release).
Some elements (currently LSRMDLTR and CWIGGLER) are not yet ported to CUDA and silently fall back to drift on the GPU build with a one-time warning.
omp Modifier Enable OpenMP parallelisation of the per-ray tracking loops in the compiled mex files (Drift, QSOS, Mult, SBend, RF, BPM, INST, LSRMDLTR, CWIGGLER).  Does NOT require the Parallel Computing Toolbox at runtime.  Compiler requirements:
  • Linux: -fopenmp (gcc / clang shipped with the distribution).
  • macOS: prefers MATLAB's bundled libomp (R2024b+, at matlabroot/bin/<arch>/libomp.dylib).  Linking against MATLAB's own copy avoids the duplicate-runtime conflict that triggers OMP: Error #179: pthread_mutex_init failed: EINVAL on the first parallel region.  The omp.h header is read from MATLAB Coder's bundle when present, else from Homebrew (brew install libomp).  If MATLAB does not ship libomp at all, the build falls back to Homebrew libomp with a warning.
  • Windows: /openmp via MSVC.
Set OMP_NUM_THREADS in the environment before starting Matlab to tune the worker count (default: hyperthread count).  Mutually exclusive with gpu.
For bit-reproducible synchrotron-radiation samples across different thread counts, call SeedLucretiaRng in serial context before each TrackThru.
fast Modifier Aggressive compiler optimisations: -O3 -march=native -ffast-math -funroll-loops -flto on Linux/macOS, /O2 /Oi /Ot /fp:fast /GL on Windows MSVC.  Combines safely with omp.  Adds compile time but typically buys 1.5-3x runtime in tracking-heavy workloads.  The fast-math flags allow associative re-ordering of floating-point sums, so reductions (BPM moments, etc.) may differ at the last few bits from the standard build.
mlrand Modifier Use Matlab's rand / randn for tracking-side random numbers (e.g. synchrotron radiation) instead of the built-in C-side xoshiro256** RNG.  MUCH slower -- only useful for cross-checking with very-old runs or when MATLAB seed control via rng() is required to match both random streams.
verbose Modifier Pass -v to the mex compiler so every command line is echoed.  Useful when diagnosing build problems.
install Action After a successful build, move the compiled mex binaries from src/mexsrc to their installed locations (src/RMatrix, src/Twiss, src/Tracking, src/LatticeVerification).  The CPU build also leaves a *_cpu.mex* copy alongside the installed file for cross-checking against a GEANT4 or GPU build of the same name.
clean Action Delete the local .o / .obj object files and the .mex* binaries before (or instead of) building.  Use this when changing targets, e.g. between cpu and gpu.
cleanall Action As clean, plus also remove the g4track static library so a subsequent cpu-g4 build forces a full rebuild.

Recommended production build (CPU):
cd src/mexsrc
build clean
build cpu omp fast install
Recommended GPU build:
cd src/mexsrc
build clean
build gpu install
(GPU is mutually exclusive with omp / fast.)
First-time macOS OpenMP setup:
brew install libomp
(One-time, before the first build cpu omp. Not needed if your MATLAB is R2024b or later, which ships its own libomp.)

First-time Linux OpenMP setup:
sudo apt install linux-tools-common linux-tools-$(uname -r)
sudo sysctl -w kernel.perf_event_paranoid=1
(The first line installs the perf profiling tool used by ProfileTrack. The second allows it to attach to a running MATLAB process. OpenMP itself only requires a gcc that supports -fopenmp, which all modern Ubuntu/RHEL toolchains do.)

Setting OMP_NUM_THREADS for optimal performance

After a successful build cpu omp install, the build script prints a machine-specific recommendation based on the detected CPU and NUMA topology.  The general rules are:

Platform Situation Recommended setting
macOS Any (Apple Silicon or Intel) Set OMP_NUM_THREADS to the physical core count (sysctl -n hw.physicalcpu).  Hyperthreads rarely help for memory-bandwidth-bound tracking and sometimes hurt.
export OMP_NUM_THREADS=$(sysctl -n hw.physicalcpu)
export OMP_PROC_BIND=close
export OMP_PLACES=cores
Linux
(standard NUMA)		 One NUMA node per socket
(lscpu shows NUMA nodes = sockets)		 Use the physical cores of one socket and bind memory locally.  Going across sockets costs 2× the memory latency.
export OMP_NUM_THREADS=$(lscpu | awk '/Core\(s\) per socket/{print $NF}')
export OMP_PROC_BIND=close
export OMP_PLACES=cores
numactl --localalloc --cpunodebind=0 matlab
Linux
(SNC enabled)		 Sub-NUMA Clustering: NUMA nodes > sockets (e.g. 2 sockets but 6 NUMA nodes, typically SNC=2 or SNC=3).  Common on AMD EPYC and Intel Sapphire Rapids servers. The correct unit is one NUMA node, not one socket.  With SNC=3 on a 72-core socket there are 3 NUMA nodes of 24 cores each -- using all 72 cores costs 3× the memory latency for 2/3 of threads.  Use numactl --localalloc to pin memory to the same node as the threads.
(SNC=3 example, 24 physical cores per NUMA node)
export OMP_NUM_THREADS=24
export OMP_PROC_BIND=close
export OMP_PLACES=cores
numactl --localalloc --cpunodebind=0 matlab
To scale across all nodes on one socket with interleaved memory:
(SNC=3, 72 cores total on socket 0 = nodes 0,1,2)
export OMP_NUM_THREADS=72
numactl --interleave=0,1,2 --cpunodebind=0,1,2 matlab
The build script detects SNC automatically and prints the specific values for your machine after an OMP build.

Why more threads can be slower:  With 144 threads on a 6-NUMA-node server, threads on node 5 access bunch arrays allocated on node 0 at twice the latency.  The parallel tracking kernels are memory-bandwidth-bound, so latency scales directly to wall time.  The optimal thread count is almost always the physical core count of one NUMA node -- not the total core count.  Once you have the per-node number, sweep it upwards:
for N in 4 8 16 24 36 48; do
  OMP_NUM_THREADS=$N numactl --localalloc --cpunodebind=0 \
    matlab -batch "load injector; tic; I.track(1,1); fprintf('N=%d t=%.1f\n',$N,toc);" 2>/dev/null
done
